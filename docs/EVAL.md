## What is measured

Each question names the document that answers it and a short answer span copied word for word from that document. For every question the evaluation retrieves the top 10 chunks and records the rank of the first chunk that comes from the right document and contains the answer span. Markdown formatting (table pipes, emphasis, backticks), line breaks and letter case are ignored in that comparison, because chunks are stored as raw markdown, and the span must not start or end in the middle of a word.

- **hit@k**: how many questions have their answer within the first k chunks.
- **MRR@10** (mean reciprocal rank): the average of 1/rank over all questions, with 0 for an answer not in the top 10. 1.000 means every answer came first; 0.500 is what you get if every answer came second.

Two chunking strategies are crossed with three retrieval modes:

- **Structure-aware** (`chunkMarkdown`): a new chunk at every heading, code blocks and tables kept whole when they fit, and the heading path ("Leave policy > Parental leave") stored with each chunk.
- **Naive fixed-size** (`chunkFixedSize`): a window of fixed size slid over the raw text, ignoring headings, tables and code.
- **Vector**: cosine similarity between the question embedding and the chunk embeddings.
- **Keyword**: Postgres full-text search over the chunk text, heading path and document title.
- **Hybrid**: both lists fused with Reciprocal Rank Fusion, the mode the chat uses.

Both strategies embed the same header in front of each chunk: the document title, then the heading path when there is one (naive chunks have none). Each strategy is indexed under its own user and searched as that user, so Row Level Security keeps the two indexes apart, exactly as it separates real users.

## Limitations

The sample is small: 6 questions, so one question moves a hit rate by about 17 percentage points, and a gap of a few questions between two rows can be noise. The questions were written by one person who had read the documents, which tends to reuse the wording of the documents and so favours keyword search; real users phrase things less predictably. A hit is decided by answer-span matching: a chunk that gives the answer in other words, or a span cut in two by a chunk boundary, counts as a miss, and a chunk that happens to contain the span counts as a hit even if it is not the best passage. Keyword scores often tie (several chunks share the top score, usually through a title or heading match), and `hybrid_search` breaks ties by the order rows happen to be stored in, so re-indexing the same chunks can move a borderline rank; the vector index (HNSW) is approximate as well. Only one embedding model (`nomic-embed-text`) and one set of chunk sizes were tested; another model or other sizes could change the ranking of the strategies. This measures retrieval only, not the quality of the answers the chat model writes from the retrieved chunks.

## Reproduce

```bash
npm run eval
```

It needs the local stack from `npm run setup` (Supabase and the embedding model running). The first run embeds the corpus once per chunking strategy; later runs reuse the stored vectors by hash and only embed the questions. Questions come from `fixtures/questions.json` (check them with `node fixtures/verify-questions.mjs`).
